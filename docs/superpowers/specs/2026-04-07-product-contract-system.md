# Product Contract System — Implementation Spec

**Date:** 2026-04-07
**Status:** Approved for implementation

---

## Problem

The system generates apps with too much surface (6-8 pages), dead CTAs, placeholder routes, and fake features. Verification is slow (10+ min) and still misses usability issues. The user receives apps that look plausible but aren't usable.

## Solution

A product contract that constrains generation, replaces the slow verification with a fast usability gate, and ensures the V1 is focused and functional.

---

## 1. Contract Schema

```typescript
interface ProductContract {
  projectName: string;
  description: string;
  technology: string;

  coreFlows: Array<{
    id: string;
    label: string;
    priority: 'primary' | 'secondary';
  }>;

  pages: Array<{
    path: string;
    role: 'home' | 'primary' | 'secondary';
    flowId?: string;
  }>;

  primaryCtas: Array<{
    id: string;
    label: string;
    page: string;
    expectedAction: 'navigate' | 'state-change' | 'submit' | 'open-modal' | 'gesture-equivalent';
    testSelector?: string;       // data-testid or CSS selector hint for gate
    blocking: boolean;
  }>;

  requiredInteractions: Array<{
    id: string;
    label: string;
    type: 'gesture' | 'navigation' | 'state-change' | 'form-save' | 'selection';
    page: string;
    testSelector?: string;
    blocking: boolean;
  }>;

  acceptanceCriteria: Array<{
    id: string;
    flowId?: string;
    type: 'page-load' | 'navigation' | 'state-change' | 'form-save' | 'gesture';
    page: string;
    successSignal: string;       // human-readable description
    checkStrategy: 'url-change' | 'dom-change' | 'modal-visible' | 'element-count' | 'form-persisted' | 'card-index-changed' | 'content-visible';
    blocking: boolean;
  }>;

  excludedFeatures: string[];
  assumptions: string[];
  dataMode: 'mock' | 'mixed' | 'real';

  featureBudget: {
    maxPages: number;            // 3-5
    maxComponents: number;       // 5-7
  };
}
```

**Where it lives:** `.drape/product-contract.json`

## 2. Contract Lifecycle

### 2a. Preview Contract (before "Crea Progetto")

Generated by a backend service — single source of truth. Frontend calls it and renders the summary; it does not independently build the contract.

**Endpoint:** `POST /ai/preview-contract`

**Input:**
```json
{
  "description": "Tinder clone",
  "technology": "nextjs",
  "answers": [
    { "question": "Core flows?", "answer": "Discover, matches, profile" },
    { "question": "Data mode?", "answer": "Mock data" },
    ...
  ]
}
```

**Logic:** Deterministic, no AI call. Parses structured answers, applies keyword extraction from description, uses conservative defaults.

**Defaults:**
- `featureBudget: { maxPages: 4, maxComponents: 6 }`
- `dataMode: 'mock'`
- `excludedFeatures: ["Video call", "Real-time chat", "Premium/payments", "Push notifications"]`
- `assumptions: ["Mock photos from Unsplash", "No real authentication", "Hardcoded mock data"]`

**Output:** `ProductContract` JSON.

### 2b. Refined Contract (during generation)

The architecture planning step receives the preview contract and may refine it.

**Refinement rules (strictly enforced):**
- May clarify labels, add implementation detail, add `testSelector` hints
- May narrow scope (remove a secondary flow, reduce page count)
- May NOT add new flows, new pages, or remove items from `excludedFeatures`
- May NOT exceed `featureBudget`

If architecture step fails, the preview contract becomes the final contract unchanged.

**Saved to:** `.drape/product-contract.json`

### 2c. Contract at Gate Time

The fast usability gate reads `.drape/product-contract.json`. It is never absent — the fallback guarantee ensures this.

## 3. Creation Flow

```
Step 1: User enters description
Step 2: 4 product-oriented questions (riformulated)
Step 3: Existing review/confirmation screen
  └─ Frontend calls POST /ai/preview-contract
  └─ Shows contract summary inline:
     • Core flows
     • Required interactions
     • Excluded features
     • Data mode / assumptions
  └─ User presses "Crea Progetto"
Step 4: Generation
  a. Architecture step → refines contract (or uses preview as fallback)
  b. Contract saved to .drape/product-contract.json
  c. Contract injected into generation prompt as hard constraint
  d. AI generates code
Step 5: CSS repair + install + build + start
Step 6: Fast usability gate (reads contract, target <90s)
  └─ NOT the current qa-agent/e2e-check 2-attempt stack
  └─ New: contract-driven usability smoke test
  └─ If fail → single autofix → fast reverify
Step 7: Unlock or block
  └─ PASS → task.status = 'completed'
  └─ FAIL → task.status = 'verification_failed'
Step 8: Deep QA (background, non-blocking)
  └─ Full qa-agent with vision, clicks, forms
  └─ Updates Project History
  └─ Does NOT affect unlock decision
```

## 4. Product-Oriented Questions

Replace current generic questions with 4 structured product questions.

**Question 1: Core Flows**
```
"Which core experiences should your V1 include?"
Options: [app-specific, generated from description]
Example for Tinder: ["Discover/swipe", "Matches list", "Chat", "Profile/settings"]
Multi-select. Maps to: contract.coreFlows
```

**Question 2: Key Interaction**
```
"What's the most important interaction?"
Options: [app-specific]
Example for Tinder: ["Swipe gesture", "Like/nope buttons", "Card stack", "List browsing"]
Single-select. Maps to: contract.requiredInteractions[0]
```

**Question 3: Data & Auth**
```
"How should data and accounts work in V1?"
Options: ["Mock data, no login", "Mock data with fake login", "Real database + auth"]
Single-select. Maps to: contract.dataMode + contract.assumptions
```

**Question 4: Visual Direction**
```
"What style fits your app?"
Options: [app-specific]
Example for Tinder: ["Dark + bold gradients", "Light + minimal", "Colorful + playful", "Professional + clean"]
Single-select. Maps to: generation prompt style hints (not contract)
```

The questions are generated by AI (as today) but with a product-oriented prompt that asks for these 4 categories specifically.

## 5. Fast Usability Gate

Replaces the current critical path (qa-agent 2 cycles + e2e-check fallback + 2 outer attempts).

### What It Checks

```
1. Page existence (all contract.pages)
   For each page: HTTP GET → 200 + has content + has CSS
   Time: ~3s per page × 4 = 12s

2. Blocking primaryCtas
   For each CTA where blocking=true:
     Navigate to cta.page
     Find element by testSelector, or by text matching cta.label
     Click it
     Verify expectedAction:
       navigate → URL changed
       state-change → DOM changed
       submit → DOM changed or URL changed
       open-modal → [role="dialog"] appeared
       gesture-equivalent → DOM changed
     If no change → FAIL
   Time: ~5s per CTA × 3 = 15s

3. Blocking acceptanceCriteria
   For each criterion where blocking=true:
     Navigate to criterion.page
     Check by checkStrategy:
       content-visible → page has >30 chars text + styled elements
       url-change → (checked via CTA click)
       dom-change → (checked via CTA click)
       modal-visible → [role="dialog"] count > 0
       element-count → querySelectorAll(selector).length > 0
       card-index-changed → (checked via interaction)
       form-persisted → (checked via interaction)
   Time: ~3s per criterion × 4 = 12s

4. Blocking requiredInteractions
   For each interaction where blocking=true:
     Navigate to interaction.page
     Find element by testSelector or infer from type
     Verify element exists and is interactive
   Time: ~3s per interaction × 2 = 6s
```

**Total: ~45-60 seconds.**

### Pass Rule

- Zero critical issues (blank page on contract page, error screen, JS fatal)
- Zero broken blocking primaryCtas
- At least one passing blocking check per primary core flow
- All blocking requiredInteractions satisfied

### Failure + Retry

If gate fails:
1. Single autofix attempt (AI reads errors + contract → fixes code)
2. Server restart
3. Fast reverify (same gate, ~60s)
4. If still fails → `verification_failed`

**Total worst case: 60s + fix(30s) + restart(10s) + 60s = ~2.5 min**

### What It Does NOT Do

- Multi-viewport testing
- Gemini Vision screenshot analysis
- Exhaustive click-through of all elements
- Form filling
- Navigation of non-contract pages

## 6. Deep QA (Non-Blocking Background)

After unlock decision, fires and forgets:

```javascript
// Fire after gate decision, do not await
runDeepQA(projectId, userId, technology).catch(err => {
  log.warn(`[DeepQA] ${projectId}: ${err.message}`);
});
```

Deep QA runs the full qa-agent.js (multi-viewport, vision, clicks, forms) and writes results to:
- `.drape/qa-report.json`
- Build report actions
- Project History

It does NOT change the unlock status.

## 7. Contract in Generation Prompt

Injected as hard constraint after the user prompt:

```
PRODUCT CONTRACT — YOU MUST FOLLOW THIS EXACTLY:

Core flows (implement these end-to-end):
{{for flow in contract.coreFlows}}
- [{{flow.priority}}] {{flow.label}}
{{endfor}}

Pages to create (ONLY these, no more):
{{for page in contract.pages}}
- {{page.path}} ({{page.role}})
{{endfor}}

Feature budget: max {{contract.featureBudget.maxPages}} pages, max {{contract.featureBudget.maxComponents}} components

Primary CTAs that MUST have real working handlers:
{{for cta in contract.primaryCtas}}
- "{{cta.label}}" on {{cta.page}} → {{cta.expectedAction}}
  {{if cta.testSelector}}Add data-testid="{{cta.testSelector}}"{{endif}}
{{endfor}}

Required interactions:
{{for interaction in contract.requiredInteractions}}
- {{interaction.label}} ({{interaction.type}}) on {{interaction.page}}
  {{if interaction.testSelector}}Add data-testid="{{interaction.testSelector}}"{{endif}}
{{endfor}}

DO NOT CREATE any of these excluded features:
{{contract.excludedFeatures.join(', ')}}

Data mode: {{contract.dataMode}}
Assumptions: {{contract.assumptions.join(', ')}}

Do NOT create pages, routes, CTAs, or features outside this contract.
Do NOT create dynamic routes like [id] unless concrete instances are navigable.
```

## 9. Tinder Clone Example — Full Trace

**User types:** "Tinder clone"

**Questions shown:**
1. Core flows? → selects: Discover, Matches, Profile
2. Key interaction? → selects: Swipe or like/nope buttons
3. Data mode? → selects: Mock data, no login
4. Visual? → selects: Dark + bold gradients

**Preview contract generated (deterministic):**
- 3 core flows (discover primary, matches primary, profile secondary)
- 4 pages: /, /discover, /matches, /profile
- 3 blocking CTAs: like, nope, match-open
- 1 blocking interaction: swipe-action
- 4 acceptance criteria (3 blocking)
- Excluded: video call, stories, premium, real-time chat
- Budget: 4 pages, 6 components

**Summary shown:** "Discover + Matches + Profile. Swipe or like/nope required. No video call, no premium. Mock photos."

**User presses "Crea Progetto"**

**Architecture step refines:** adds testSelector hints (data-testid="like-btn"), clarifies component list. Does NOT add chat or video call.

**Generation:** AI builds exactly 4 pages, 6 components, with data-testid on CTAs.

**Fast gate (60s):**
- / → 200, content, CSS ✓
- /discover → 200, content, CSS ✓
- /matches → 200, content, CSS ✓
- /profile → 200, content, CSS ✓
- Click like-btn → DOM changes (card disappears) ✓
- Click nope-btn → DOM changes ✓
- Click match-open → navigates to detail ✓
- **PASS → unlock**

**Deep QA (background):** full qa-agent with vision runs, finds "spacing tight on matches page" → logged to History, does not block.
